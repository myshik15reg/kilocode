# Обзор (карта процессов)

Этот файл - точка входа в пакет WorkFlowAI для Kilo Code: как стартовать задачи, когда нужен протокол, какие процессы запускать и как валидировать качество.

## Как запускать процессы в Kilo Code

- Любой файл из `~/.kilocode/workflows/` можно запустить как воркфлоу, набрав в чате: `/имя-файла.md`.
- Воркфлоу - это инструкция. Агент сам предложит чтение/правки/команды и запросит подтверждения согласно настройкам авто-аппрува (Auto-Approve).
- Начни с `/quickref.md`, затем используй `/protocol-new.md` или профильные процессы по ситуации.

## Базовый цикл работы (для любой задачи)

1. Контекст:
    - Прочитай `.kilocode/memory-bank/index.md`.
    - Подтверди контекст строкой: `[MB: OK]`.
    - (Опционально) Для 2-step подготовки и краткой сводки: `/context-priming.md`.
2. Классификация:
    - Тривиально (1 файл, не более 10 строк, без изменения поведения/публичного API) - протокол обязателен, но план может быть минимальным.
    - Всё остальное - протокол обязателен с полноценным планом.
3. Протокол (если нужен):
    - Создать: `/protocol-new.md`.
    - Продолжить: `/protocol-resume.md`.
    - Ревью и закрыть: `/protocol-review-merge.md`.
4. Выполнение:
    - Выбери режим (см. ниже) и делай маленькие итерации.
    - После каждого шага обновляй `.protocols/.../plan.md` и фиксируй решения в `.protocols/.../execution.md`.
5. Гейты качества:
    - Тесты и покрытие 100% (lines/branches/functions).
    - Линтер 0 ошибок и 0 предупреждений.
    - Безопасность: базовый чеклист OWASP, если применимо.
6. Завершение:
    - Обнови Memory Bank (если изменился контекст/правила/архитектура).
    - Запусти диагностику пакета (см. раздел "Диагностика").

## Режимы Kilo Code (коротко)

- `ask` - вопросы и анализ без правок.
- `architect` - планирование и документация (обычно без правок кода).
- `code` - реализация.
- `debug` - систематическая отладка.
- `orchestrator` - декомпозиция на подзадачи и делегирование (через `new_task`).

Подсказка:

- Для длинных задач используй оркестрацию, чтобы не раздувать контекст одной сессии.
- Для разных фаз можно закреплять разные модели за режимами (Sticky Models).

## Как выбрать процесс

Используй `/quickref.md` как меню. Типовые случаи:

- Инцидент/прод-авария: `/hotfix-emergency.md`.
- Новая функциональность: `/protocol-new.md` (опционально: `/spec-driven-development.md`).
- Рефакторинг: `/refactoring-workflow.md`.
- Документация: `/documentation-workflow.md`.
- Деплой: `/deployment-workflow.md`.
- Миграции БД: `/migration-workflow.md`.
- Исключение из правил (крайний случай): `/waiver-workflow.md`.

## Workflow Decision Tree

Используй это дерево для быстрого выбора процесса и режима.

```
START: Какой тип задачи?
|
+-- [Production incident?]
|   YES -> /hotfix-emergency.md -> debug -> code-fixer -> reviewer
|
+-- [Вопрос/исследование?]
|   YES -> ask или planning/research-*
|   |
|   +-- [Нужен код?]
|       NO -> завершить в ask
|       YES -> создать протокол -> orchestrator
|
+-- [1C:Enterprise?]
|   YES -> /protocol-new.md -> 1c-orchestrator (см. /1c-testing-workflow.md)
|
+-- [Задача требует код?]
    |
    +-- [Тривиально? (1 файл, <=10 строк, без изменения поведения)]
    |   YES -> минимальный протокол -> *-dev (специалист по стеку)
    |
    +-- [Сложная/multi-file?]
        YES -> /protocol-new.md
        |
        +-- [Новая фича?]
        |   -> orchestrator -> architect -> *-dev -> *-tester -> reviewer
        |
        +-- [Рефакторинг?]
        |   -> /refactoring-workflow.md -> architect -> refactorer -> reviewer
        |
        +-- [Bug fix?]
        |   -> debug -> code-fixer -> *-tester -> reviewer
        |
        +-- [Миграция БД?]
            -> /migration-workflow.md -> data-architect -> *-dev
```

### Quick Mode Selection

| Ситуация                     | Режим              | Примечание                               |
| ---------------------------- | ------------------ | ---------------------------------------- |
| Не знаю с чего начать        | `ask`              | Уточни требования                        |
| Нужен план                   | `architect`        | Создаст протокол                         |
| Сложная задача с подзадачами | `orchestrator`     | Декомпозирует и делегирует               |
| Реализация (любой стек)      | `*-dev` специалист | НЕ используй `code` если есть специалист |
| Тесты                        | `*-tester`         | unit/integration/e2e/security            |
| Code review                  | `reviewer`         | Финальная проверка                       |
| Отладка                      | `debug`            | Найти причину бага                       |
| Исправление бага             | `code-fixer`       | После debug                              |
| Локализация                  | `translate`        | i18n файлы                               |
| 1C (любая задача)            | `1c-orchestrator`  | Он выберет специалиста                   |

## Для Windows/PowerShell: практические правила

- Не полагайся на `&&` в примерах команд (в PowerShell это частая причина ошибок). Предпочитай отдельные команды или `;`.
- Избегай Unicode-стрелок (например, `U+2192`, `U+2190`, `U+2194`) в текстах и шаблонах. Используй ASCII: `->`, `<-`, `<->`.

