# Деплой

Процесс для безопасного деплоя в окружения (staging/production) с упором на предсказуемость, наблюдаемость и откат.

## Когда использовать

- Любой выпуск в окружение, которое влияет на пользователей/клиентов.
- Любые изменения, которые затрагивают инфраструктуру, конфигурацию, миграции, публичные API.

## Принципы

- Сначала качество: тесты/линтер/типизация до деплоя.
- Предсказуемость: деплой по плану, без "сюрпризов" в процессе.
- Наблюдаемость: метрики и логи должны подтвердить, что всё стабильно.
- Откат должен быть понятным и быстрым.

## Входные данные (если нет - спроси)

- Что деплоим: ветка/тег/коммит, список изменений.
- Куда деплоим: окружение (staging/prod), регион/кластер, окно деплоя.
- Как деплоим: механизм (CI/CD, скрипт, кнопка, GitOps), стратегия (rolling/canary/blue-green).
- Есть ли миграции БД: да/нет (если да - сначала `/migration-workflow.md`).
- Критерии успеха и критерии отката.

## Шаги

### Шаг 1: Подготовка

1. Зафиксируй цель и окно деплоя (когда, кто в курсе, кто на связи).
2. Проверь, что изменения согласованы и готовы:
    - нет незавершённых задач/PR в составе релиза;
    - есть понятные release notes (хотя бы кратко).
3. Зафиксируй план отката:
    - к какой версии откатываемся;
    - что будет с миграциями/данными;
    - кто принимает решение об откате.

### Шаг 2: Локальная валидация (до деплоя)

1. Прогони быстрые гейты качества (пример, адаптируй под проект):

```powershell
npm test
npm run lint
npm run typecheck
```

2. Если тестов нет или покрытие не гарантировано - остановись и сделай минимум, чтобы не деплоить "вслепую".

### Шаг 3: Деплой в staging (если есть)

1. Выполни деплой в staging и дождись готовности.
2. Выполни smoke-тесты и минимум проверок:
    - ключевые эндпоинты/фичи;
    - логин/авторизация (если применимо);
    - критичные фоновые джобы (если есть).
3. Если staging отсутствует - явно зафиксируй риск и усили наблюдаемость на проде.

### Шаг 4: Деплой в production

1. Выбери стратегию:
    - Rolling update: по умолчанию для большинства сервисов.
    - Canary: если нужно снизить риск и есть маршрутизация трафика.
    - Blue/green: если можно держать две версии параллельно.
2. Выполни деплой и наблюдай за состоянием:
    - health checks;
    - error rate;
    - latency;
    - ключевые метрики домена (если есть).

### Шаг 5: Верификация после деплоя

1. Подтверди функциональность (smoke на проде).
2. Подтверди стабильность по метрикам/логам на интервале (например, 15-30 минут).
3. Зафиксируй итог:
    - что деплоили и куда;
    - время;
    - результат;
    - ссылки на логи/дашборды (если есть).

### Шаг 6: Откат (если нужно)

Откат выполняй только по явным критериям (не "на всякий случай").

1. Останови дальнейший rollout (если он постепенный).
2. Выполни откат на предыдущую стабильную версию.
3. Проверь, что проблема ушла.
4. Зафиксируй постмортем (см. `/hotfix-emergency.md` -> пост-инцидент).

## Контрольный список (перед продом)

- [ ] Гейты качества пройдены (тесты/линтер/типизация).
- [ ] Есть план отката и ответственный.
- [ ] Понимаем, есть ли миграции БД (если да - они согласованы и безопасны).
- [ ] Включена наблюдаемость (логи/метрики доступны).
- [ ] Есть smoke-набор для проверки.
