# Рабочий процесс: Создание нового протокола (protocol-new)

## Назначение

Протокол — это **временный workspace** для задачи. Хранит все артефакты: планы, промежуточные результаты, архитектуру. После завершения — подтверждение и удаление.

## Lifecycle протокола

```
CREATE → WORK → COMPLETE → CONFIRM → DELETE
   │        │       │          │         │
   │        │       │          │         └─► Удаление после подтверждения
   │        │       │          └─► Спросить пользователя
   │        │       └─► Все задачи выполнены
   │        └─► Артефакты в artifacts/
   └─► brief.md + plan.md
```

## Как определить глубину протокола

Протокол обязателен всегда. Критерии ниже нужны, чтобы понять, насколько подробным должен быть план.

Считай задачу нетривиальной, если выполняется хотя бы одно:

- меняется поведение/логика/публичный API
- затрагивается более 1 файла или добавляются новые файлы
- меняются зависимости, конфиги, CI/скрипты, миграции
- изменения касаются безопасности/перформанса/данных

Если сомневаешься - считай задачу нетривиальной и делай более подробный план.

## Входные данные

- Название задачи (краткий slug)
- Краткое описание требований

## Выходные данные

- `.protocols/YYYY-MM-DD-name/` с заполненными файлами
- (опционально) worktree и draft PR

### mini vs mini-wt (worktree)

- **mini:** работа последовательно в текущей ветке (проще, если задача одна)
- **mini-wt:** отдельный `git worktree` для параллельной задачи (если нужно распараллелить)

Подсказка: если результаты делаются параллельно — **вливай их последовательно** (merge-queue mindset), чтобы не накапливать конфликты.

См. также: [`../rules/git-workflow-rules.md`](../rules/git-workflow-rules.md)

## Структура протокола

```
.protocols/YYYY-MM-DD-name/
├── brief.md           # Требования, DoD
├── plan.md            # План выполнения
├── execution.md       # Лог выполнения (опционально)
├── context.md         # Локальный контекст (опционально)
└── artifacts/         # ВСЕ промежуточные артефакты
    ├── architecture/  # Архитектурные решения
    │   ├── draft-v1.md
    │   └── final.md
    ├── research/      # Исследования
    │   └── findings.md
    ├── designs/       # Дизайн-документы
    │   └── api-spec.md
    └── reviews/       # Результаты review
        └── review-report.md
```

## Артефакты в протоколе

**ВСЕ промежуточные результаты** хранятся в `artifacts/`:

| Тип          | Папка                     | Примеры                    |
| ------------ | ------------------------- | -------------------------- |
| Архитектура  | `artifacts/architecture/` | draft-v1.md, adr-001.md    |
| Исследования | `artifacts/research/`     | findings.md, benchmarks.md |
| API дизайн   | `artifacts/designs/`      | api-spec.md, schema.json   |
| Review       | `artifacts/reviews/`      | review-report.md           |
| Тесты        | `artifacts/tests/`        | test-plan.md               |
| Другое       | `artifacts/`              | любые файлы                |

**Принцип:** Протокол — это sandbox. Всё что нужно для задачи, хранится здесь. После завершения — удаляется.

## Шаг 1: Проверка окружения

1. Убедись, что `main` чист: `git status`.
2. Если есть незавершенные изменения - согласуй с пользователем.

## Шаг 2: Создание протокола

1. Создай директорию `.protocols/YYYY-MM-DD-name/`.
2. Создай файлы `brief.md`, `plan.md`, `execution.md`.
3. При необходимости добавь `context.md`.

**Автоматизация (необязательно):** можно сгенерировать каркас протокола скриптом:

```powershell
powershell -ExecutionPolicy Bypass -File "$HOME/.kilocode/workflowai/scripts/workflowai-new-protocol.ps1" -ProjectPath . -Name "feature-name" -WithContext
```

Локальный вариант (если pack встроен в репозиторий):

```powershell
powershell -ExecutionPolicy Bypass -File "scripts/workflowai-new-protocol.ps1" -ProjectPath . -Name "feature-name" -WithContext
```

## Шаг 3: Заполнение brief.md

Минимальный шаблон:

```markdown
# Название фичи

## Требования

- [ ] R1 ...
- [ ] R2 ...

## Принципы проектирования и стиля

- [ ] Не усложнять решение: без оверинжиниринга при сохранении требуемой функциональности.
- [ ] Решать проблемы самым простым способом.
- [ ] Использовать и переиспользовать существующие сущности; не создавать новые без необходимости.
- [ ] Доверять фреймворкам и не делать ненужных слоев оберток.
- [ ] Не вводить слои абстракции без необходимости.

## Критерии готовности (DoD)

- [ ] Покрытие = 100% (строки/ветвления/функции)
- [ ] Линтер: 0 ошибок / 0 предупреждений
- [ ] Чеклист безопасности пройден
- [ ] Документация обновлена
```

## Шаг 4: Заполнение plan.md

Обязательные элементы:

- шаги, зависимости, файлы к изменению
- матрица покрытия требований
- пометка параллельных задач `[P]`
- статусы задач: `[ ]` не начато, `[~]` в работе, `[x]` сделано

Шаблон:

```markdown
# План

## Шаги

- [ ] Фаза 1 ...
- [ ] Фаза 2 ...

## Проверка фаз (необязательно)

- [ ] Ручная проверка фазы 1 (шаги + ожидаемый результат)
- [ ] Ручная проверка фазы 2 (шаги + ожидаемый результат)

## Файлы к изменению

- path/to/file.ext

## Матрица покрытия требований

| Требование | Задачи     |
| ---------- | ---------- |
| R1         | T001, T002 |

## Список задач (если задача большая)

- [ ] T001 [P] [US1] ... (path/to/file)
- [ ] T002 [US1] ... (зависит от T001)
```

## Мини-чеклист декомпозиции

- [ ] Каждое требование [R#] покрыто задачей
- [ ] Задачи атомарные (30 мин - 4 часа)
- [ ] В каждой задаче указаны файлы и критерии завершения
- [ ] Параллельные задачи помечены `[P]`

## Шаг 5: Делегирование

После готовности протокола делегируй реализацию в Code Mode через `new_task`.

Если `new_task` недоступен (например, в Codex CLI), выполни роль-петлю в одной сессии (plan -> implement -> test -> review) и фиксируй прогресс в протоколе (исключение из "one mode per task").

## Шаг 6: Завершение протокола

После выполнения всех задач:

### 1. Проверь завершённость

```markdown
## Checklist завершения

- [ ] Все задачи в plan.md отмечены [x]
- [ ] Тесты проходят (100% coverage)
- [ ] Code review пройден
- [ ] Документация обновлена (если требуется)
- [ ] Memory Bank обновлён (если были архитектурные изменения)
```

### 2. Покажи изменения и запроси подтверждение

```
Задача завершена:
- Протокол: .protocols/YYYY-MM-DD-name/
- Выполнено: [краткое описание]

Изменённые файлы:
  M src/components/Button.tsx
  M src/components/Button.test.tsx
  A src/utils/helpers.ts

Хотите зафиксировать изменения в git?
- Да, создать коммит
- Нет, только подтвердить завершение
- Отмена (продолжить работу)
```

### 3. При подтверждении коммита

```bash
# Показать diff для review
git diff --stat

# Создать коммит (conventional commits)
git add <files>
git commit -m "feat(component): add Button component

- Add Button with variants
- Add unit tests (100% coverage)
- Add Storybook stories

Co-Authored-By: Claude <noreply@anthropic.com>"
```

### 4. После подтверждения — удали протокол

```bash
rm -rf .protocols/YYYY-MM-DD-name/
```

**ВАЖНО:**

- НЕ удаляй протокол без подтверждения пользователя
- НЕ коммить без подтверждения пользователя
- Если нужно сохранить артефакты — перенеси их ДО удаления
- Memory Bank обновляется ДО удаления протокола

---

## Полный flow завершения

```
1. Все задачи выполнены
   │
2. git status (показать изменения)
   │
3. Запросить подтверждение:
   │  - Коммит + удалить протокол
   │  - Только удалить протокол
   │  - Отмена
   │
4. Если коммит:
   │  - git add <files>
   │  - git commit -m "..."
   │
5. Перенести важные артефакты (если есть)
   │
6. Удалить протокол
   │
7. Готово
```

## Что переносить перед удалением

| Артефакт                            | Куда переносить                         | Когда                    |
| ----------------------------------- | --------------------------------------- | ------------------------ |
| Архитектурные решения               | `.kilocode/memory-bank/architecture.md` | Значимые изменения       |
| API спецификации                    | `docs/api/`                             | Публичные API            |
| ADR (Architecture Decision Records) | `docs/adr/`                             | Важные решения           |
| Остальное                           | Удаляется                               | Промежуточные результаты |
