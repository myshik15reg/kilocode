# 1C (firm): SDLC «Заявка → DONE» (1c-alfa-sdlc)

## Назначение

Дать повторяемый фирменный SDLC для разработки 1С: этапы, артефакты и гейты.

## Источник (firm SoT)

- Этапы процесса: [`REG`](../sources/1c-alfa/reg.md#sdlc)

## Важные определения

### Поддержка vs проект

Классификация по оценке времени кодирования:

- поддержка: < 1 часа
- проектная: > 1 часа

Основание: [`REG`](../sources/1c-alfa/reg.md#sdlc-task-classification)

---

## Этапы и обязательные результаты (DoD)

> Примечание: ниже перечислены **минимальные** артефакты, которые прямо указаны в регламенте.

### 1) Заявка

**Что происходит:** регистрация и формулирование требований.

**DoD (артефакты в УЗ):**

- понятное описание требований
- виза руководителя заказчика (если требуется)
- прикреплённый файл с требованиями
- для «поддержки» — предложенное решение в УЗ

Основание: [`REG`](../sources/1c-alfa/reg.md#sdlc-stages)

### 2) Аналитика (для проектных задач)

**Что происходит:** уточнение требований, согласование, сценарии тестирования.

**DoD (артефакты в УЗ):**

- согласованные финальные требования
- согласованное ТЗ (только для проектных задач)
- оценка эффекта заказчиком (только для проектных задач)
- согласованные сценарии тестирования (только для проектных задач)

Основание: [`REG`](../sources/1c-alfa/reg.md#sdlc-stages)

### 3) Архитектура (для проектных задач)

**Что происходит:** design review, оценка сроков, (при необходимости) Archimate.

**DoD (артефакты в УЗ):**

- design review (согласованная концепция)
- предварительная оценка по срокам
- задокументированное архитектурное решение (модель данных)

Основание: [`REG`](../sources/1c-alfa/reg.md#sdlc-stages)

### 4) Разработка

**Гейт:** все изменения должны быть описаны разработчиком в «Базе изменённых объектов» заявки.

**DoD:** заполнена «База изменённых объектов».

Основание: [`REG`](../sources/1c-alfa/reg.md#sdlc-development-gate-changed-objects)

### 5) Тестирование

Этап состоит из двух частей:

- ИТ‑тестирование
- бизнес‑тестирование заказчиком/представителем

**Гейт:** после тестирования заказчик письменно подтверждает корректную работу функционала или возвращает на доработку.

**DoD:** письмо с подтверждением от заказчика, что функционал протестирован и его можно переносить в продуктив.

Основание: [`REG`](../sources/1c-alfa/reg.md#sdlc-testing-gate)

### 6) Code review

**Гейт:** перенос в продуктив — только после успешного CR.

**DoD:** документ Code review со статусом «пройден успешно» / «замечания устранены».

Основание: [`REG`](../sources/1c-alfa/reg.md#sdlc-release-gate-code-review)

### 7) Документация

**DoD:** пользовательская документация (по фирменному шаблону) размещена в согласованном месте.

Основание: [`REG`](../sources/1c-alfa/reg.md#sdlc-stages)

### 8) Релиз

**Гейт:** в продуктив должен попасть только код, который:

- успешно прошёл CR
- описан в учётной системе

Основание: [`REG`](../sources/1c-alfa/reg.md#sdlc-stages)

### 9) ОПЭ

**DoD:** письмо от заказчика/руководителя разработки с подтверждением реализации в продуктиве.

Основание: [`REG`](../sources/1c-alfa/reg.md#sdlc-stages)

### 10) DONE

Этап наступает после письменного подтверждения реализации.

Основание: [`REG`](../sources/1c-alfa/reg.md#sdlc-stages)
