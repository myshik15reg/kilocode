# Полный SDLC для 1С-задач (1c-full-sdlc)

> Полный цикл разработки 1С-задач с обязательной глубокой аналитикой на каждом этапе.
> Оркестратор НЕ делает аналитику — только маршрутизирует.

## Цель

Обеспечить качественную разработку 1С через последовательный проход всех этапов:

- глубокая аналитика перед каждым решением,
- тесное взаимодействие между агентами через Handoff,
- гейты качества на каждом переходе.

## Когда использовать

**Полный цикл (9 этапов):**

- Проектные задачи (> 1 часа кодирования)
- Новая функциональность
- Изменения критичной бизнес-логики
- Интеграции с внешними системами

**Сокращённый цикл (3 этапа):**

- Поддержка (< 1 часа кодирования)
- Локальное изменение (1-2 модуля)
- Решение очевидно

**Экспресс цикл (4 этапа):**

- Hotfix P0/P1 (критичный баг в продуктиве)
- Авторизовано руководством

### Этап 1: Заявка (1c-orchestrator)

**Агент:** `1c-orchestrator`
**Задача:** Классификация и маршрутизация.
**НЕ делает аналитику — только определяет тип и направляет.**

**Действия:**

1. Прочитать Memory Bank (brief.md, context.md)
2. Классифицировать задачу:
    - Проектная (> 1 час) → полный цикл
    - Поддержка (< 1 час) → сокращённый цикл
    - Hotfix (P0/P1) → экспресс цикл
3. Создать протокол (`.protocols/YYYY-MM-DD-task-name/`)
4. Сформировать `brief.md`
5. Делегировать первому агенту в цепочке

**Артефакты:**

```
.protocols/YYYY-MM-DD-task-name/
├── brief.md              # Описание, классификация, DoD
├── plan.md               # План этапов (заполняется далее)
└── execution.md          # Лог выполнения (пустой)
```

**GATE 1:** Тикет создан, классификация определена, протокол создан.

**Подтверждение:** `[1C-ORCH: CLASSIFIED → {тип цикла}, DELEGATED → {агент}]`

---

### Этап 2: Бизнес-анализ (1c-business-analyst)

**Агент:** `1c-business-analyst`
**Задача:** Глубокий анализ бизнес-требований.

**Обязательный метод: Dual Analysis**

- **Generator:** Формирует решение, User Stories, AC
- **Critic:** Находит риски, edge cases, противоречия
- **Improve:** Улучшает решение на основе критики

**Действия:**

1. Прочитать `brief.md` + Memory Bank
2. Собрать бизнес-требования (BRD)
3. Написать User Stories с Acceptance Criteria
4. Провести Dual Analysis (Generator + Critic)
5. Определить нефункциональные требования
6. Определить критерии успеха
7. Сформировать Handoff для СА

**Артефакты:**

```
.protocols/.../artifacts/analysis/
├── business-analysis.md      # BRD: цель, аудитория, ценность
├── user-stories.md           # US-001, US-002, ... с AC (ДАНО/КОГДА/ТОГДА)
├── acceptance-criteria.md    # Полный список AC
└── dual-analysis-notes.md    # Риски, edge cases, митигации
```

**Структура business-analysis.md:**

```markdown
# Бизнес-анализ: [Название]

## Executive Summary

- Цель: [что и зачем]
- Целевая аудитория: [кто будет использовать]
- Бизнес-ценность: [какую проблему решаем]

## User Stories

### US-001: [Название] (P1)

КАК [роль]
Я ХОЧУ [функционал]
ЧТОБЫ [бизнес-ценность]

Критерии приёмки:

1. ДАНО [состояние], КОГДА [действие], ТОГДА [результат]
2. ДАНО [состояние], КОГДА [действие], ТОГДА [результат]

## Функциональные требования

| ID    | Требование | Приоритет |
| ----- | ---------- | --------- |
| FR-01 | ...        | High      |

## Нефункциональные требования

- Производительность: [время отклика]
- Безопасность: [права доступа]

## Dual Analysis Notes

- Выявленные риски: [список]
- Edge cases: [список]
- Стратегия митигации: [список]

## Критерии успеха

- SC-01: [измеримый результат]
```

**GATE 2:** BRD утвержден, User Stories есть, AC определены, Dual Analysis проведён.

**Handoff:** → `1c-system-analyst`

---

### Этап 3: Системный анализ (1c-system-analyst)

**Агент:** `1c-system-analyst`
**Задача:** Преобразование бизнес-требований в техническое задание.

**Обязательный метод: Mental Simulation**

- Мысленный прогон каждого сценария
- Поиск точек отказа
- Проверка алгоритмов на граничных условиях

**Действия:**

1. Прочитать `business-analysis.md` + `user-stories.md`
2. Определить объекты метаданных (новые/изменяемые)
3. Спроектировать структуру данных
4. Описать алгоритмы в псевдокоде
5. Описать интеграционные взаимодействия
6. Провести Mental Simulation
7. Выполнить Impact Analysis
8. Сформировать Handoff для Архитектора

**Артефакты:**

```
.protocols/.../artifacts/analysis/
├── technical-solution.md     # ТЗ: объекты, структура, алгоритмы
├── data-model.md             # Структура данных (реквизиты, типы)
├── algorithms.md             # Алгоритмы в псевдокоде
├── integrations.md           # Интеграции (HTTP, RabbitMQ, COM)
└── impact-analysis.md        # Влияние на существующий функционал
```

**Структура technical-solution.md:**

```markdown
# Техническое задание: [Название]

## Объекты метаданных

### Новые объекты

| Тип | Имя | Синоним | Назначение |
| --- | --- | ------- | ---------- |

### Изменяемые объекты

| Объект | Что меняется | Причина |
| ------ | ------------ | ------- |

## Структура данных

[Детальные реквизиты каждого объекта]

## Алгоритмы (псевдокод)

[Пошаговое описание, НЕ BSL-код]

## Интеграции

[HTTP-сервисы, RabbitMQ, COM]

## Impact Analysis

| Модуль | Влияние | Тип | Риск |
| ------ | ------- | --- | ---- |

## Mental Simulation

### Сценарий: [название]

1. Вход: [что происходит]
2. Шаг: [действие]
   ...

### Точки отказа

- [условие] → [что произойдет] → [митигация]
```

**GATE 3:** ТЗ согласовано, алгоритмы в псевдокоде, Impact Analysis готов.

**Handoff:** → `1c-architect`

### Этап 4: Архитектура (1c-architect)

**Агент:** `1c-architect`
**Задача:** Проектирование архитектуры решения.

**Обязательный метод: Design Review + ADR**

- Design Review по чеклисту (SOLID, связность, БСП, производительность)
- ADR для каждого нестандартного решения

**Действия:**

1. Прочитать `technical-solution.md` + `data-model.md`
2. Спроектировать модульную архитектуру
3. Определить взаимодействие модулей
4. Создать ADR для нестандартных решений
5. Провести Design Review
6. Определить риски и митигации
7. Сформировать Handoff для разработчика

**Артефакты:**

```
.protocols/.../artifacts/design/
├── architecture.md           # Архитектура: модули, взаимодействие
├── adr-001-*.md             # ADR для нестандартных решений
└── design-review.md          # Результат Design Review
```

**GATE 4:** Design Review OK, ADR созданы, риски митигированы.

**Handoff:** → Этап 5: Написание решения (skill `task-solution`)

---

### Этап 5: Написание решения (skill task-solution)

**Агент:** `1c-architect` (применяет skill `task-solution`)
**Задача:** Формализация детального решения перед реализацией.

**Обязательный метод: task-solution skill**

- Глубокий анализ кодовой базы перед написанием
- Структурированный документ с блоками верификации
- Примеры кода, запросы, особенности реализации
- Повелительное наклонение ("Создать", "Добавить")

**Действия:**

1. Прочитать `architecture.md` + `technical-solution.md` + `data-model.md`
2. Изучить существующий код (аналогичный функционал, паттерны проекта)
3. Применить skill `.kilocode/skills/task-solution/SKILL.md`
4. Сформировать `solution.md` с блоками:
    - **Краткое описание** — суть задачи и решения
    - **Блок верификации** — изменения, затронутые объекты, логика работы, зависимости
    - **Блок вспомогательной информации** — примеры кода, запросы, особенности
5. Сохранить в `.protocols/.../solution.md`
6. Показать пользователю для верификации
7. Сформировать Handoff для разработчика

**Артефакты:**

```
.protocols/.../
├── solution.md               # Детальное решение (skill task-solution)
```

**Структура solution.md:**

```markdown
# Решение по задаче [НОМЕР]

## Краткое описание

[1-3 предложения]

---

## Блок описания для верификации

### Изменения

1. [Объект и местоположение]: [что сделать] - [описание логики]

### Затронутые объекты метаданных

- [ТипОбъекта.ИмяОбъекта] - [что изменено/добавлено]

### Логика работы

[Подробное описание: что происходит, какие данные, какой результат]

### Зависимости и связи

[Связанные объекты, используемые данные, влияние изменений]

---

## Блок вспомогательной информации

### Примеры кода

[Фрагменты BSL с указанием местоположения]

### Запросы

[Примеры запросов к данным]

### Особенности реализации

[Нюансы, на которые обратить внимание]
```

**GATE 5:** `solution.md` создан, блоки верификации заполнены, пользователь подтвердил.

**Handoff:** → `1c-developer` / `1c-kd-developer` / `1c-form-designer`

### Этап 6: Реализация (1c-developer)

**Агент:** `1c-developer` / `1c-kd-developer` / `1c-form-designer`
**Задача:** Реализация согласно архитектуре.

**Обязательный метод: TDD (Red → Green → Refactor)**

- Сначала тест, потом код
- jdocstring для экспортных методов
- Комментарии к изменениям (`// + Альфа-Лизинг...`)

**Действия:**

1. Прочитать `architecture.md` + `technical-solution.md`
2. Реализовать код по TDD
3. Заполнить Базу измененных объектов
4. Пройти АПК (0 errors, 0 warnings)
5. Сформировать Handoff для тестировщика

**Артефакты:**

```
.protocols/.../artifacts/implementation/
├── changed-objects.md        # База измененных объектов
├── code-samples/             # Ключевые фрагменты кода
└── implementation-log.md     # Лог реализации
```

**GATE 6:** Код написан, База изм. объектов заполнена, АПК = 0 errors.

**Handoff:** → `1c-tester`

---

### Этап 7: Тестирование (1c-tester + 1c-vanessa-tester)

**Агенты:** `1c-tester` (xUnitFor1C) + `1c-vanessa-tester` (Vanessa Automation)
**Задача:** Полное тестирование решения.

**Обязательный метод: Coverage Analysis + Edge Case Mining**

- Unit-тесты (xUnitFor1C): 100% coverage
- BDD-сценарии (Vanessa): критичные пользовательские пути
- Бизнес-тестирование: письменное подтверждение заказчика

**Действия:**

1. `1c-tester`: Unit-тесты по AAA (Arrange-Act-Assert)
2. `1c-vanessa-tester`: BDD-сценарии (Gherkin)
3. Бизнес-тестирование на тестовой базе
4. Получить письменное подтверждение заказчика
5. Сформировать Handoff для ревьюера

**Артефакты:**

```
.protocols/.../artifacts/testing/
├── test-plan.md              # План тестирования
├── xunit-tests/              # Unit-тесты
├── vanessa-features/         # BDD сценарии
├── coverage-report.md        # Покрытие: 100%
└── business-approval.md      # Подтверждение заказчика
```

**GATE 7:** Coverage 100%, все тесты green, бизнес-подтверждение получено.

**Handoff:** → `1c-quality-specialist`

---

### Этап 8: Code Review (1c-quality-specialist)

**Агент:** `1c-quality-specialist`
**Задача:** Проверка качества кода и соответствия требованиям.

**Обязательный метод: Quality Gate Check**

- Стандарты именования (ал\_ префикс)
- jdocstring для экспортных методов
- Комментарии к изменениям
- SOLID принципы
- Безопасность (OWASP)
- Производительность (запросы, N+1)
- АПК / SonarQube

**Действия:**

1. Проверить соответствие `brief.md` (требования)
2. Проверить стандарты кодирования
3. Проверить безопасность
4. Проверить производительность
5. Проверить тесты и покрытие
6. Запустить АПК / SonarQube
7. Вынести вердикт (Approved / Request Changes)

**Артефакты:**

```
.protocols/.../artifacts/review/
├── code-review.md            # Вердикт + комментарии
├── quality-checklist.md      # Чеклист качества
└── apk-report.md             # Отчёт АПК / SonarQube
└── findings.json             # Structured findings по vendored review contract
```

**GATE 8:** CR Approved, Quality checklist OK, АПК отчёт чист.

Review MUST follow [`1c-review-pack.md`](1c-review-pack.md:1) and produce `findings.json`.

**Handoff:**

- Если **Approved** → `1c-orchestrator` (релиз)
- Если **Request Changes** → `1c-developer` (исправления)

---

### Этап 9: Релиз (1c-orchestrator)

**Агент:** `1c-orchestrator`
**Задача:** Координация релиза и закрытие задачи.

**Действия:**

1. Собрать результаты всех этапов
2. Подготовить release notes
3. Координировать перенос в продуктив
4. Получить подтверждение ОПЭ
5. Обновить Memory Bank
6. Закрыть протокол

**Артефакты:**

```
.protocols/.../artifacts/release/
├── release-notes.md          # Описание релиза
├── deployment-checklist.md   # Чеклист развертывания
└── ope-confirmation.md       # Подтверждение ОПЭ
```

**GATE 9:** Релиз в продуктив, ОПЭ подтверждено, Memory Bank обновлён → DONE.

## Сокращённый цикл (поддержка < 1 час)

```
Заявка → Реализация + Тест → Code Review → DONE
```

| #   | Этап              | Агент                        | Что делает                |
| --- | ----------------- | ---------------------------- | ------------------------- |
| 1   | Заявка            | `1c-orchestrator`            | Классификация = поддержка |
| 2   | Реализация + Тест | `1c-developer` → `1c-tester` | TDD, Coverage 100%        |
| 3   | Code Review       | `1c-quality-specialist`      | Стандарты, АПК            |

**Условия применения:**

- < 1 час кодирования
- 1-2 модуля
- Решение очевидно
- Не затрагивает критичную бизнес-логику

---

## Экспресс цикл (hotfix P0/P1)

```
Заявка (URGENT) → Архитектор (Express) → Реализация + Тест → Review (Express) → DONE
```

| #   | Этап              | Агент                        | Что делает                            |
| --- | ----------------- | ---------------------------- | ------------------------------------- |
| 1   | Заявка            | `1c-orchestrator`            | Классификация = hotfix                |
| 2   | Архитектор        | `1c-architect`               | Express анализ, Root Cause, мин. план |
| 3   | Реализация + Тест | `1c-developer` → `1c-tester` | Минимальный fix, TDD                  |
| 4   | Review            | `1c-quality-specialist`      | Ускоренный CR                         |

**Условия применения:**

- Критичный баг в продуктиве
- Бизнес-блокер
- Авторизовано руководством

---

## Анти-паттерны

- **Пропуск БА/СА:** Начинать кодирование без анализа → некачественное решение
- **Оркестратор-аналитик:** Оркестратор сам анализирует вместо делегирования → размытие ответственности
- **Без Handoff:** Не передавать контекст следующему агенту → потеря информации
- **Без Gate:** Пропускать гейты качества → дефекты в продуктиве
- **Сокращение для проектных задач:** Применять сокращённый цикл для задач >1 час → технический долг
