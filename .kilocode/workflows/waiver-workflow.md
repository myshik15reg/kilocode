# Исключения из правил (waiver)

По умолчанию в WorkFlowAI действует политика нулевой терпимости. Исключение (waiver) - крайняя мера, когда соблюдение правила объективно невозможно или есть критический инцидент.

## Цель

Сделать исключения управляемыми: явными, ограниченными по времени, с ответственным и планом возврата к норме. Исключение должно снижать риск, а не узаконивать техдолг.

## Что считается исключением

Временное, явно одобренное отклонение от правила (например: покрытие ниже 100%, предупреждения линтера, временное ослабление шага CI) с обязательным планом возврата к норме.

## Когда допустимо (редко)

- Инцидент P0/P1 или hotfix, когда нужно быстро восстановить сервис (см. `hotfix-emergency.md`).
- Внешние ограничения, не зависящие от команды: vendor/generated код, инструменты без нужных настроек, flaky зависимости (временно).
- Миграции legacy, когда невозможно одномоментно довести модуль до 100% без остановки бизнеса, но есть "минимальный разрез" и план закрытия.

## Когда запрещено

- "Так быстрее", "потом поправим", "слишком сложно".
- Для нового кода (новый код должен соответствовать правилам).

## Обязательные условия

Без этих пунктов исключение недействительно:

- Есть протокол `.protocols/YYYY-MM-DD-name/` (если это не чистый инцидентный hotfix) и он ведётся.
- Есть тикет/issue `#123` (без тикета нельзя).
- Указаны: объём работ, риск, меры снижения риска, срок действия, владелец.
- Исключение явно упомянуто в PR/ревью и одобрено ответственным.
- В `plan.md` есть задачи на снятие исключения и сроки.

## Где хранить waiver

Рекомендуется хранить waiver рядом с протоколом, чтобы не "тащить" исключение в другие проекты:

- `.protocols/YYYY-MM-DD-name/waivers/waiver-123.md`

Если протокол не ведётся (допустимо только для инцидента):

- запись в `execution.md` + тикет.

## Шаги

1. Попробуй соблюсти правило (TDD/coverage/lint). Зафиксируй попытки и почему не вышло.
2. Создай тикет `#123` с причиной и критичностью.
3. Создай файл исключения по шаблону ниже.
4. Получи одобрение (reviewer/owner). Без одобрения - нельзя.
5. Сделай минимально возможный обходной путь, не расширяя объём работ.
6. Добавь задачи на устранение (в `plan.md`) и сроки.
7. Сними исключение: вернуть правила -> закрыть тикет -> обновить Memory Bank (если влияет на процесс/архитектуру).

## Шаблон файла исключения

```markdown
# Исключение #123: [короткое название]

## Какое правило ослабляем

- Например: покрытие 100% по веткам для модуля X

## Область применения (где и что временно допускается)

- Файлы/пути: [ ... ]
- Что именно разрешено временно: [ ... ]

## Причина (почему неизбежно)

[объективные ограничения; ссылки на логи/доки]

## Риски

[что может пойти не так; влияние]

## Меры снижения риска

[мониторинг, доп. тесты в другом месте, план раскатки, фича-флаг и т.п.]

## План снятия исключения

- Дедлайн: YYYY-MM-DD
- Задачи: [T001, T002, ...]
- Ответственный: [имя/роль]

## Одобрение

- Одобрил(а): [имя/роль]
- Дата: YYYY-MM-DD
```
