# Навык: Написание решения по задаче

## Назначение

Навык для систематизированного описания решения по задаче разработки 1С. Создаёт структурированный документ с блоками верификации и вспомогательной информации. Работает как с уже реализованными задачами (ретроспективное документирование), так и с новыми задачами (планирование реализации).

## Триггеры

Используй этот навык, когда:

- Нужно задокументировать решение по задаче
- Требуется описание для верификации выполненных изменений
- Необходимо подготовить техническое описание перед реализацией
- Пользователь просит "написать решение по задаче"
- Требуется формализовать техническое описание для передачи коллегам

## Контекст

Перед применением прочитать:

- `.kilocode/memory-bank/brief.md` - контекст проекта
- `.kilocode/memory-bank/tech.md` - технический стек (если есть)
- `.kilocode/memory-bank/architecture.md` - архитектура (если есть)

## Результат (Output)

1. Создан (или обновлён) файл решения в протоколе задачи:

`./.protocols/YYYY-MM-DD-УЗ-XXXX/solution.md`

2. Решение согласовано с заказчиком/стейкхолдерами (через секцию «Вопросы для согласования» и подтверждение/правки по обратной связи).

> Важно: если в разделе «Верификация по ТЗ» остаются пункты со статусом `Вопрос` или `Риск`, документ считается **черновиком (Draft) / на согласовании** и **не должен** восприниматься как завершённое решение.

> Важно: не включай в итоговый документ секреты, токены, внутренние URL, пароли и любые данные доступа.

## Процедура

### Шаг 0: Подготовить протокол

Если протокола по задаче ещё нет — создай каталог `.protocols/YYYY-MM-DD-УЗ-XXXX/` и заведи минимум:

- `brief.md` — что делаем и какой DoD
- `plan.md` — план (1-2 шага достаточно)
- `execution.md` — лог решений/уточнений

### Шаг 1: Запросить номер задачи

Спроси у пользователя номер задачи (например, УЗ №1234 или произвольный идентификатор).

### Шаг 2: Определить тип задачи

Уточни, это уже реализованная задача или новая задача для планирования.

**Варианты:**

1. **Реализованная задача** - требуется описать уже сделанные изменения
2. **Новая задача** - требуется спланировать и описать будущую реализацию

### Шаг 3A: Для РЕАЛИЗОВАННОЙ задачи

> **КРИТИЧЕСКИ ВАЖНО:**
>
> - Описывай **ТОЛЬКО ФАКТЫ** - то, что реально было сделано
> - **НИЧЕГО НЕ ПРИДУМЫВАЙ** и не додумывай
> - Вся информация должна быть получена **ТОЛЬКО** из git, кода или MCP
> - Если информации недостаточно - запроси у пользователя, но НЕ выдумывай
> - Каждое утверждение должно быть подтверждено источником (коммит, файл, MCP)

#### 3A.1: Поиск по git

Найди коммиты, связанные с задачей:

```bash
# Кросс-платформенно: ограничиваем количество строк опцией Git
git log --oneline --all --grep="УЗ-XXXX" -n 20
git log --oneline --all --grep="XXXX" -n 20
```

Посмотри изменённые файлы в найденных коммитах:

```bash
git show --stat <commit-hash>
git diff <commit-hash>~1 <commit-hash>
```

#### 3A.2: Поиск по кодовой базе

Если коммиты не найдены или нужна дополнительная информация:

- Выполни поиск по номеру задачи в комментариях кода
- Найди связанные файлы по названию функционала
- Проанализируй изменённые модули/объекты
- **Читай код** чтобы понять что именно было изменено

#### 3A.3: Поиск через MCP 1c-task-extractor (если доступен)

Если настроен MCP-сервер 1c-task-extractor:

- Запроси информацию о задаче через MCP
- Получи связанные метаданные и описание

#### 3A.4: Поиск по репозиторию и другие инструменты

Если предыдущие шаги не дали достаточно информации:

**Вариант A (кросс-платформенно через Git):**

```bash
# `git grep` — команда Git (работает в Windows/macOS/Linux)

# Поиск по номеру задачи во всех файлах репозитория
git grep -n "УЗ-XXXX"
git grep -n "XXXX"

# Поиск по ключевым словам из названия задачи
git grep -n -i "ключевое_слово"
```

**Вариант B (Windows PowerShell):**

```powershell
# Поиск по всем файлам в каталоге проекта
Get-ChildItem -Recurse -File | Select-String -Pattern "УЗ-XXXX"
Get-ChildItem -Recurse -File | Select-String -Pattern "ключевое_слово" -CaseSensitive:$false
```

Также можно использовать:

- Поиск по IDE
- Поиск по имени метода/объекта
- Анализ истории изменений файлов

#### 3A.5: Анализ изменений

На основе **собранных фактов**:

- Определи изменённые объекты метаданных
- Выдели ключевые изменения в логике (читая код!)
- Определи затронутые формы и интерфейсы
- **Опиши логику так, как она реально работает в коде**

### Шаг 3B: Для НОВОЙ задачи

> **КРИТИЧЕСКИ ВАЖНО:**
>
> - **Максимально изучи кодовую базу** перед написанием решения
> - Решение должно быть **оптимальным и профессиональным**
> - Следуй **стандартам и рекомендациям 1С**
> - Используй существующие механизмы и паттерны проекта

#### 3B.1: Запросить постановку задачи / ТЗ (обязательно)

Попроси пользователя предоставить **ТЗ целиком** (полный текст со всеми пунктами/приложениями) и явно зафиксировать, что является источником требований.

Минимальный набор входных данных:

- ТЗ/постановка задачи: полный текст требований
    - функциональные требования
    - данные/реквизиты
    - формы, обработки, отчёты
    - права доступа
    - интеграции
    - регламентные задания
    - ограничения
    - требования к производительности и UX
- Бизнес-цель и ожидаемый результат (что считается успешным результатом)
- Ограничения и вводные (версии/контуры, совместимость с типовым/существующим функционалом, запреты)

**Проверка качества ТЗ (обязательно перед написанием решения):**

- Если в ТЗ есть пробелы/противоречия/нехватка данных — сформулируй уточняющие вопросы и зафиксируй их в разделе «Вопросы для согласования».
- До получения ответов **не утверждай решение как завершённое**: пометь соответствующие пункты в «Верификация по ТЗ» статусом `Вопрос`.

#### 3B.2: Запросить ссылку на Confluence (опционально)

Если есть документация в Confluence:

- запроси ссылку и/или экспорт страницы (текст/Markdown/PDF);
- при наличии доступа без секретов можно использовать браузер/инструменты чтения (например, Playwright) для извлечения текста;
- **не** вставляй в итоговое решение токены, внутренние URL и любые данные доступа.

#### 3B.3: Глубокий анализ кодовой базы

**Обязательно выполни:**

1. **Поиск аналогичного функционала:**

    - Найди похожие реализации в проекте
    - Изучи как решаются подобные задачи
    - Выяви используемые паттерны

2. **Анализ существующих объектов:**

    - Какие объекты метаданных уже есть
    - Какие общие модули используются
    - Какие подсистемы затрагиваются

3. **Изучение архитектуры:**

    - Как организована структура модулей
    - Какие есть слои (клиент/сервер)
    - Как организована работа с данными

4. **Проверка зависимостей:**
    - Какие объекты связаны с изменяемыми
    - Что может сломаться при изменениях

#### 3B.4: Применение стандартов 1С

При проектировании решения учитывай:

**Архитектура:**

- Разделение клиент-серверного кода
- Минимизация вызовов сервера
- Использование асинхронных вызовов где возможно

**Производительность:**

- Оптимальные запросы (без соединений в цикле)
- Пакетная обработка данных
- Кэширование повторно используемых данных

**Качество кода:**

- Понятные имена переменных и методов на русском языке
- Комментарии для сложной логики
- Разбиение на небольшие методы

**Безопасность:**

- Проверка прав доступа
- Валидация входных данных
- Использование параметров в запросах

#### 3B.5: Запросить дополнительную информацию

Если чего-то не хватает:

- Уточни граничные условия
- Запроси примеры данных
- Уточни интеграционные требования

```markdown
## Блок описания для верификации

### Назначение блока

Этот блок — «техническое ядро» решения: по нему проверяют, **что именно** должно быть сделано (или что уже сделано) и **где именно** это находится в конфигурации/коде.

Реальный стиль из корпуса решений: чаще всего это список пунктов с явным указанием объектов, условий и алгоритма; при сложных задачах — подробный пошаговый разбор (вплоть до полей, регистров, временных таблиц, фильтров).

### Что обязательно указать (чеклист)

- [ ] **Изменения по объектам (обязательный минимум):** для каждого изменения указать _что меняем_ + _где_ + _зачем/какой эффект_ + _ключевые условия срабатывания_.
- [ ] **Алгоритм / логика работы:** последовательность шагов «если/то», точки входа (запись, проведение, команда формы, регламентное задание, обработчик обмена и т.п.).
- [ ] **Данные и источники:** какие регистры/справочники/документы/настройки используются; какие поля/отборы критичны.
- [ ] **Границы и побочные эффекты:** что _не_ меняем; какие объекты могут быть затронуты; обратная совместимость.
- [ ] **Ошибки и крайние случаи:** что делать при отсутствующих данных, некорректных значениях, дублях, конкурентных изменениях.
- [ ] **Адаптивная детализация:**
    - если изменений мало и логика простая — достаточно 3–10 пунктов «Изменения»;
    - если много объектов / сложный расчёт / СКД / массовая обработка / интеграция — добавь подробный алгоритм (шаги, условия, списки полей/параметров/VT, критерии отбора).
- [ ] **Git-сверка (только для реализованных задач при наличии привязки):** перечислить коммиты и кратко сверить, что описанные изменения соответствуют _фактическим_ изменениям по `git show --stat` и/или сохранённым diff/статистике (файлы/объекты/тип изменений). Не вставлять большие diff целиком.

### Правила оформления Markdown (как в корпусе реальных решений)

- Изменения оформляй **нумерованными пунктами** или **маркированным списком** (пункты должны быть самодостаточными).
- Локации указывай строкой «объект → место → метод», например:
    - `ОбщийМодуль.<Имя> (Сервер) → Процедура/Функция <Имя>()`
    - `Документ.<Имя> → Форма <ИмяФормы> → МодульФормы → Процедура <Имя>()`
    - `Отчет.<Имя> → СКД/Макет → (что именно меняем)`
- Названия объектов, полей, методов, статусов, параметров — в `коде` (backticks).
- Если изменений много — используй таблицу:

    | Объект / место | Что меняем | Условия / эффект | Примечание |
    | -------------- | ---------- | ---------------- | ---------- |

- Не используй HTML (если исходник в HTML — переведи в Markdown).

### Мини-шаблон (вставь и заполни)

#### Изменения (минимальный каркас)

- `[...]`: что меняем; где; условия; ожидаемый эффект.

#### Алгоритм / логика работы (если > 1–2 шагов)

1. ...
2. ...
3. ...

#### Данные и условия

- Источники данных: ...
- Ключевые поля/отборы/параметры: ...

#### Зависимости / влияние

- Связанные объекты/подсистемы: ...
- Риски/ограничения: ...

#### Привязка к git (если есть)

- Коммиты: `<hash> — сообщение`, ...
- Сверка: список файлов/объектов из `--stat` соответствует пунктам выше (OK/есть расхождения → описать).

## Блок вспомогательной информации

### Назначение блока

Сюда складываются материалы, которые реально встречаются в решениях и помогают реализации/разбору: перечни затронутых объектов, списки изменённых запросов, пояснения «почему так», примеры/заготовки, настройки, параметры интеграций, оценки трудозатрат.

Этот блок **не заменяет** формальное описание изменений, а дополняет его.

### Что обязательно указать (чеклист)

- [ ] **Изменения в запросах / СКД (если есть):** перечислить, где менялись тексты запросов/поля/параметры/VT (без копирования огромных полотен — лучше ссылка на место/имя функции/макета).
- [ ] **Перечень объектов и точек правок (если много):** список документов/справочников/ОМ/форм/регистров/обработок/ролей.
- [ ] **Данные для проверки/воспроизведения (если применимо):** критерии отбора, тестовые условия, «как увидеть проблему/результат».
- [ ] **Интеграции/обмены (если применимо):** какие правила/очереди/ключи/пакеты/события задействованы (без URL/токенов/логинов).
- [ ] **Массовые обработки/регламентные задания (если применимо):** отбор, пакетность, ретраи, логирование, окна выполнения.
- [ ] **Связанные задачи/история решения (если есть):** перечислить идентификаторы задач/решений, на которые опираемся (формат `УЗ-XXXXX`, без внутренних ссылок).
- [ ] **Оценка трудозатрат/релиз (если это принято):** грубая оценка по этапам + что входит в тест/релиз.

> Если нужна воспроизводимая оценка трудозатрат именно в **человеко‑часах** по тексту решения + git‑прокси, используй отдельный skill: [`effort-estimation-human-hours/SKILL.md`](../effort-estimation-human-hours/SKILL.md:1).

### Правила оформления Markdown

- Для перечней используй таблицы или списки; для «много объектов» — предпочтительна таблица.
- Код/запросы/фрагменты допускаются **только если они короткие** и критичны для понимания; оформляй fenced-блоком с языком (`1c`/`bsl`/`sql`).
- Внутренние URL/адреса/доступы не писать: вместо этого указывать **полное имя метаданных** и путь в конфигурации/IDE.
- Допущения и спорные моменты помечай явно: `Допущение:` / `Нужно уточнить:`.

## Верификация по ТЗ (обязательно)

> Цель: формально доказать, что **каждый пункт ТЗ** отражён в решении, и что решение не содержит «догадок» без явной фиксации допущений.

### Мэппинг требований ТЗ → элементы решения

Заполни таблицу **по каждому пункту ТЗ**. Если пункты ТЗ не пронумерованы — пронумеруй их сам (с сохранением исходной формулировки в кратком виде).

| Пункт ТЗ | Требование (кратко) | Где отражено в решении (раздел/пункты)            | Статус             | Комментарий / допущение |
| -------- | ------------------- | ------------------------------------------------- | ------------------ | ----------------------- |
| 1        | ...                 | `Блок описания для верификации → Изменения → ...` | OK / Вопрос / Риск | ...                     |

**Правила:**

- Если требование закрывается «условно» (нужно уточнение) — статус `Вопрос`, без попыток «додумать» реализацию.
- Если закрытие возможно, но есть существенный риск (производительность, совместимость, данные) — статус `Риск`.
- Если решение содержит шаг «сделать X», который не следует напрямую из ТЗ — добавь это как **отдельное допущение** и вынеси в отчёт (и/или в вопросы для согласования).

### Логическая проверка сценариев и крайних случаев

Прогони логически (мысленно) основные сценарии и зафиксируй проверки:

- пустые/некорректные данные, дубли
- конкурентное изменение данных
- откаты транзакций
- обработка ошибок и сообщения пользователю
- корректность движений по регистрам, проведений документов, заполнения реквизитов
- соответствие типам данных, корректность запросов/отборов
- совместимость с типовым функционалом и стандартами разработки 1С

### Краткий отчёт верификации (добавлять всегда)

- **Покрытие требований:** X/Y пунктов ТЗ со статусом `OK`; список `Вопрос`/`Риск`.
- **Открытые вопросы/неопределённости:** (перечень)
- **Допущения (ничего не «по догадке»):** (перечень)
- **Риски и что уточнить перед внедрением:** (перечень)
```

## Лучшие практики

### Стиль написания

**Всегда используй повелительное наклонение:**

- Пиши "Создать", "Добавить", "Реализовать" - даже если задача уже реализована
- НЕ пиши "Создан", "Добавлен", "Реализован"
- Решение - это инструкция к действию, а не отчёт о проделанной работе

**Описывай логику работы подробно:**

- Не просто указывай название метода - опиши что он делает и как
- Если изменена часть логики - опиши как будет работать после изменения
- Опиши входные параметры и возвращаемое значение

**Плохо (сухо):**

```
- ОбщийМодуль.блРаботаСФайламиCRM: добавлен метод НаличиеВыписокПоПроекту()
```

**Хорошо (с описанием логики):**

```
- ОбщийМодуль.блРаботаСФайламиCRM: добавить метод НаличиеВыписокПоПроекту(Проект) -
  метод принимает ссылку на проект, выполняет запрос к регистру сведений ВыпискиПоПроектам,
  проверяет наличие записей со статусом "Загружена".
  Возвращает Истина если найдена хотя бы одна такая выписка, иначе Ложь.
  Используется для проверки возможности закрытия проекта.
```

### Терминология 1С

- Вместо "процедура" или "функция" пиши **"метод"**
- При изменении кода указывай **точное местоположение модуля**:
    - `Справочник.XXX, модуль объекта` - для модуля объекта
    - `Справочник.XXX, модуль менеджера` - для модуля менеджера
    - `Документ.XXX, форма ФормаДокумента, модуль формы` - для модуля формы
    - `ОбщийМодуль.XXX` - для общего модуля
    - `Обработка.XXX, форма Форма, модуль формы` - для форм обработок

### Для реализованных задач

- Описывай **ТОЛЬКО то, что видишь в коде/коммитах**
- Не додумывай и не предполагай
- Если что-то неясно - лучше спроси у пользователя
- Каждый пункт должен быть подтверждён источником

### Для новых задач

- Изучи существующий код перед написанием решения
- Используй существующие паттерны проекта
- Следуй стандартам разработки 1С
- Предлагай оптимальное решение с точки зрения производительности
- Учитывай масштабируемость и поддерживаемость

## Диагностика и решения

### Проблема: Не найдены коммиты по номеру задачи

**Решение:**

- Попробуй поиск по разным форматам номера (УЗ №123., УЗ-123, 123)
- Поищи по ключевым словам из названия задачи
- Запроси у пользователя хеш коммита напрямую

### Проблема: Недостаточно информации для описания

**Решение:**

- Задай уточняющие вопросы пользователю
- Проанализируй код более детально
- **НЕ ВЫДУМЫВАЙ** - лучше оставить пробел чем написать неправду

### Проблема: Слишком много изменений для одного документа

**Решение:**

- Разбей на логические блоки
- Создай несколько документов по подзадачам
- Сделай общий документ со ссылками на детальные

````
## Краткое описание

Реализовать механизм автоматического уведомления менеджеров о просроченных задачах

**Источник требований:** [ТЗ / описание в УЗ]

## Блок описания для верификации

### Изменения

- Создать РегламентноеЗадание.УведомлениеОПросроченныхЗадачах:
   - Расписание: каждый час в рабочее время (9:00-18:00, Пн-Пт)
   - Обработчик: ОбщийМодуль.УведомленияСервер.ОбработатьПросроченныеЗадачи()
   - Использование: включено по умолчанию

- ОбщийМодуль.УведомленияСервер: добавить метод ОбработатьПросроченныеЗадачи() -
   точка входа регламентного задания. Получает список просроченных задач через
   метод НайтиПросроченныеЗадачи(), группирует по ответственным, для каждого
   ответственного вызывает ОтправитьУведомлениеОтветственному()

- ОбщийМодуль.УведомленияСервер: добавить метод НайтиПросроченныеЗадачи() -
   выполняет запрос к Справочник.Задачи, отбирает записи где Статус = "В работе"
   и ПлановаяДатаЗавершения < ТекущаяДата(). Проверяет по регистру сведений
   ИсторияУведомлений что с момента последнего уведомления прошло достаточно времени
   (интервал из настроек). Возвращает таблицу значений с колонками: Задача, Ответственный, СрокИстек

- ОбщийМодуль.УведомленияСервер: добавить метод ОтправитьУведомлениеОтветственному(Ответственный, СписокЗадач) -
   формирует текст уведомления со списком просроченных задач, отправляет email через
   существующий механизм РаботаСПочтой.ОтправитьПисьмо(), отправляет push через
   СистемаУведомлений.ОтправитьPush(). Записывает факт отправки в регистр ИсторияУведомлений

- Создать РегистрСведений.ИсторияУведомленийОЗадачах:
   - Измерения: Задача (СправочникСсылка.Задачи), Ответственный (СправочникСсылка.Пользователи)
   - Ресурсы: ДатаПоследнегоУведомления (Дата)
   - Назначение: хранение даты последнего уведомления для предотвращения спама

- Константа.НастройкиУведомлений: добавить в структуру настроек:
   - УведомлятьОПросроченныхЗадачах (Булево) - флаг включения механизма
   - ИнтервалПовторныхУведомленийЧасы (Число) - минимальный интервал между
     повторными уведомлениями по одной задаче (по умолчанию 24 часа)

### Логика работы

Регламентное задание запускается каждый час в рабочее время. При запуске:

1. Проверяется флаг УведомлятьОПросроченныхЗадачах в настройках. Если выключен - выход.

2. Выполняется запрос к справочнику Задачи - отбираются задачи со статусом "В работе",
   у которых плановая дата завершения меньше текущей даты.

3. Для каждой найденной задачи проверяется регистр ИсторияУведомленийОЗадачах -
   если с момента последнего уведомления прошло меньше времени чем указано в настройках
   (ИнтервалПовторныхУведомленийЧасы), задача пропускается.

4. Оставшиеся задачи группируются по ответственному менеджеру.

5. Каждому ответственному отправляется одно письмо со списком всех его просроченных задач
   и одно push-уведомление.

6. После успешной отправки в регистр ИсторияУведомленийОЗадачах записывается текущая дата
   для каждой задачи.
````

````
### Логика работы

При записи/проведении договора лизинга система проверяет обязательность заполнения «ПредметЛизингаМИС» для корпоративного сегмента.

При создании новой версии договора значение «ПредметЛизингаМИС» переносится из предыдущей версии. При обновлениях версии значение не перезаписывается, если уже заполнено (если это требование подтверждено заказчиком).

При загрузке из интеграции поле заполняется по согласованному источнику. Если запрещено перетирание, загрузка обновляет поле только при пустом значении либо по явному признаку «разрешить обновление».

Фоновая очередь/регламентное задание дозаполняет поле для исторических данных (в рамках правил), логирует результаты и ошибки.

Отчёт «Портфель ДЛ» выводит «ПредметЛизингаМИС» для аналитики.
````
