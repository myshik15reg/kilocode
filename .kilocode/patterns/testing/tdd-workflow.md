# TDD Workflow: The Red-Green-Refactor Cycle

> **Принцип:** "No Test = No Code". Мы не пишем реализацию без падающего теста.

## 1. Цикл TDD (Red-Green-Refactor)

### 🔴 RED: Напиши падающий тест

1. **Цель:** Определить желаемое поведение интерфейса до реализации.
2. **Действия:**
    - Создать новый тест-файл или добавить `test case`.
    - Написать минимальный код теста, который вызывает несуществующую функцию или проверяет новое условие.
    - Запустить тесты и убедиться, что он **падает** (Compilation Error или Assertion Error).
3. **Критерий:** Тест должен падать именно по той причине, которую мы ожидаем (например, "Function not found" или "Expected 200, got 404").

### 🟢 GREEN: Сделай тест проходящим

1. **Цель:** Заставить тест пройти как можно быстрее.
2. **Действия:**
    - Написать **минимально необходимый код**.
    - Не думать об архитектуре или чистоте кода на этом этапе.
    - Hardcode значений допустим, если это решает задачу теста (будет исправлено на Refactor).
3. **Критерий:** Все тесты (включая новый) проходят.

### 🔵 REFACTOR: Улучши код

1. **Цель:** Убрать технический долг, не ломая тесты.
2. **Действия:**
    - Убрать дублирование (DRY).
    - Улучшить имена переменных.
    - Выделить методы/классы (SRP).
    - Оптимизировать алгоритм.
3. **Критерий:** Все тесты остаются зелеными после изменений.

## 2. Агентное взаимодействие в TDD

### Роль: Code Mode (Developer)

- Пишет Unit-тесты и реализацию.
- Следует циклу RGR самостоятельно для небольших модулей.

### Роль: Unit Tester (Assistant)

- Может быть вызван для написания тестов _перед_ реализацией (стратегия Test-First).
- **Задача:** "Напиши тесты для функции X, которая должна делать Y".

### Роль: QA Engineer (Integration/E2E)

- Пишет интеграционные тесты _после_ стабилизации API.
- Не участвует в RGR цикле unit-тестирования, но проверяет сценарии использования.

## 3. Практические правила

1. **Baby Steps:** Тест должен проверять одно небольшое изменение. Не пишите тест на 100 строк сразу.
2. **Test Behavior, Not Implementation:** Тестируйте публичный контракт, а не приватные методы.
3. **Isolation:** Unit-тесты не должны ходить в сеть или базу (используйте моки).
4. **Integration Tests:** Должны проверять реальное взаимодействие (БД, API) в изолированном окружении (Testcontainers).

## 4. Пример (Python/Pytest)

### RED

```python
# test_calculator.py
def test_add():
    assert add(2, 3) == 5  # NameError: name 'add' is not defined
```

### GREEN

```python
# calculator.py
def add(a, b):
    return 5  # Fake implementation just to pass
```

### REFACTOR (после добавления test_add(1,1))

```python
# calculator.py
def add(a, b):
    return a + b  # Real implementation
```
