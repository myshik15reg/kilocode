# Evidence Rules (SoT)

## Goal

Этот документ задаёт правила доказательности для AlfaFlowAI: что считать фактом, как ссылаться на источники, как маркировать предположения, как предотвращать галлюцинации.

## Normative language

1. MUST означает обязательное требование.
2. MUST NOT означает запрещённое действие.
3. SHOULD означает рекомендацию; отклонение допускается только при явной причине, зафиксированной как evidence.
4. MAY означает опциональное действие.

## Definitions

| Term | Definition | Canonical ref |
|---|---|---|
| evidence | Проверяемое утверждение/факт с указанием источника. | [`Terminology`](terminology.md:1) |
| fact | Утверждение, которое можно проверить по доступному источнику без интерпретации. | Этот документ |
| assumption | Утверждение, которое нельзя проверить по доступным источникам в репозитории или во входных данных задачи. | Этот документ |
| source | Артефакт, который можно открыть и проверить: файл в репозитории, лог, отчёт, шаблон, ссылка на внешний документ (если разрешено задачей). | Этот документ |

## Rule 1: Facts MUST be sourced

1. Любое утверждение уровня "так устроено" или "такой файл существует" MUST сопровождаться источником.
2. Источник MUST быть одним из:
   1) ссылка на файл в репозитории;
   2) ссылка на конкретный фрагмент файла (строки);
   3) ссылка на артефакт в `.protocols/.../artifacts/` (если речь о текущей задаче);
   4) ссылка на stable evidence в `.kilocode/evidence/` (если речь о пакете/стандарте).

## Rule 2: Assumptions MUST be explicit

1. Если факт нельзя подтвердить источником, утверждение MUST быть помечено как `ASSUMPTION:` и иметь безопасное значение по умолчанию.
2. Любое `ASSUMPTION:` MUST содержать:
   1) что именно предполагается;
   2) почему нет источника;
   3) какой риск даёт предположение;
   4) какое безопасное поведение выбирается по умолчанию.

## Rule 3: No hallucinated files

1. Агент MUST NOT ссылаться на файлы, которые не существуют в репозитории.
2. Если в документе нужно упомянуть потенциальный файл (например, `./scripts/...` в consuming project), он MUST быть маркирован как "условный" и сопровождаться правилом проверки существования.

## Rule 4: Link format MUST be consistent

1. Внутренние ссылки SHOULD использовать относительные пути.
2. Ссылка SHOULD указывать строку, если это возможно и полезно для проверки.
3. Для примеров путей MUST различать:
   1) workflow-pack embedded: `.kilocode/...`;
   2) global install: `~/.kilocode/...` (Unix) и `$HOME/.kilocode/...` (PowerShell);
   3) consuming project: `./.github/...` и `./scripts/...`.

## Rule 5: Evidence location MUST be stable

1. Evidence, на которое ссылаются правила/SoT, MUST жить в `.kilocode/evidence/`.
2. Rules/SoT MUST NOT зависеть от `temp/`.
3. Rules/SoT MUST NOT зависеть от исторических протоколов в `.protocols/`.
4. Если evidence возникает в ходе задачи, оно SHOULD быть перенесено из `.protocols/.../artifacts/` в `.kilocode/evidence/...` до удаления протокола.

## Rule 6: How to ask clarifying questions

1. Если критичный пробел нельзя закрыть фактами, агент MUST задать ровно один точный вопрос.
2. До ответа MUST действовать безопасное правило по умолчанию с пометкой `TEMP:`.
3. `TEMP:` правило MUST быть минимальным и обратимым.

## Minimal checklist (self-verify)

| Check | Pass criteria |
|---|---|
| No hallucinated paths | Все упомянутые пути существуют, либо явно отмечены как условные для consuming project |
| Assumptions explicit | Каждый не подтверждённый пункт помечен `ASSUMPTION:` и имеет безопасный default |
| Stable evidence | Ссылки на доказательства ведут в `.kilocode/evidence/` или в текущий протокол |
