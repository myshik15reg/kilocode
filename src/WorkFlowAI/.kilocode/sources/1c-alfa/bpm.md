<a id="start-point"></a>
## Точка старта (MUST)

<a id="start-unique-name"></a>
### Уникальное имя

**MUST:** Необходимо указать уникальное имя точки старта строкой; желательно понятное и читаемое. Заполняется без пробелов.

Источник:
- `3.2.+Точка+старта.doc`, «3.2.4.4. Точка старта. Имя элемента графической схемы»

<a id="start-readable-title"></a>
### Читаемое наименование

**MUST:** Необходимо указать понятное и читаемое название элемента графической схемы; желательно, чтобы оно было схоже по смыслу с именем элемента.

Источник:
- `3.2.+Точка+старта.doc`, «3.2.4.5. Точка старта. Наименование элемента схемы»

<a id="start-variant-choice"></a>
### Выбор варианта точки старта

**MUST:** Выбирать «Старт из объекта», если планируется стартовать бизнес‑процесс из объекта.

**MUST:** Выбирать «Независимый старт бизнес‑процесса», если планируется стартовать процесс программно (из встроенного объекта конфигурации / из внешней команды и т.д.).

Источник:
- `3.2.+Точка+старта.doc`, «3.2.4.6. Точка старта. Вариант точки старта»

<a id="start-object"></a>
### Объект старта

**MUST:** Необходимо выбрать параметр бизнес‑процесса из ПВХ параметров; у выбранного объекта на форме появится кнопка «Бизнес‑процессы».

Источник:
- `3.2.+Точка+старта.doc`, «3.2.4.7. Точка старта. Объект старта»

<a id="start-expression-typo"></a>
### Произвольное выражение: критичная особенность

**MUST:** В тексте программного кода для произвольного выражения есть опечатка: необходимо писать не `РезультатВычисления`, а `РеузльтатВычисления`. Если написать корректно, произвольное выражение не будет выполнено.

Источник:
- `3.2.+Точка+старта.doc`, «3.2.4.13. Точка старта. Произвольное выражение»

<a id="start-error-text"></a>
### Текст ошибки

**MUST:** Текст ошибки должен быть понятным пользователю и объяснять, почему возникла ошибка и бизнес‑процесс не стартовал.

Источник:
- `3.2.+Точка+старта.doc`, «3.2.4.14. Точка старта. Текст ошибки»

<a id="end-point"></a>
## Точка завершения (MUST)

**MUST:** Необходимо указать уникальное имя точки завершения строкой; желательно понятное и читаемое. Заполняется без пробелов.

**MUST:** Необходимо указать понятное и читаемое название элемента графической схемы; желательно, чтобы оно было схоже по смыслу с именем элемента.

Источник:
- `3.3.+Точка+завершения.doc`, «3.4.1.4. Имя элемента графической схемы»
- `3.3.+Точка+завершения.doc`, «3.4.1.5. Наименование элемента схемы»

---

<a id="action-point"></a>
## Точка действия (MUST)

**MUST:** Пример персональной/ролевой адресации должен быть понятен: при персональной адресации указывается конкретный пользователь; при ролевой — роль и подразделение.

Источник:
- `3.4.+Точка+действия.doc`

---

<a id="condition-point"></a>
## Точка условия (MUST)

**MUST:** Обработчик проверки условия обязателен и контролируется при проверке карты маршрута перед сохранением бизнес‑процесса.

Источник:
- `3.5.+Точка+условия.doc`

---

<a id="choice-point"></a>
## Точка выбора варианта (MUST)

**MUST:** Обработчик выбора варианта обязателен и контролируется при проверке карты маршрута перед сохранением бизнес‑процесса.

**MUST:** Для корректной настройки необходимо настроить каждый вариант в табличной части (двойной клик по каждой строке) и заполнить параметры.

Источник:
- `3.6.+Точка+выбора+варианта.doc`

---

<a id="merge-point"></a>
## Точка слияния (MUST)

**MUST:** Бизнес‑процесс не выполняется дальше точки слияния, пока все входящие ветви не будут пройдены; точка слияния — этап, на котором должны быть завершены все задачи по разделённым веткам.

Источник:
- `3.7.+Точка+разделения+и+слияния.doc`

---

<a id="processing-point"></a>
## Точка обработки (MUST)

**MUST:** В сценарии «Создание договора страхования (однократное выполнение)» обязательно наличие карточки доп. услуг, иначе договор не будет создан.

Источник:
- `3.8.+Точка+обработки.doc`, «3.8.1.6. Вариант автоматической обработки»

---

<a id="scheduled-jobs"></a>
## Регламентные задания бизнес‑процессов (MUST)

**MUST:** Проверка «многократное выполнение» необходима, так как вариант обработки «МногократноеВыполнение» работает многопоточно с помощью отложенных заданий.

Источник:
- `4.+Управляющие+регламентные+задания+бизнес-процессов.doc`, «4.5. ... многократное выполнение»

---

<a id="engine-modules"></a>
## Модули/методы движка (CRM) (MUST)

**MUST:** Метод `лкРегламентныеЗадания.ПровестиДиагностикуЗависшихПроцессов` выполняет комплексную проверку зависших бизнес‑процессов, требующих вмешательства.

**MUST:** Метод `лкРегламентныеЗадания.ал_АвтозавершениеБизнесПроцессов` обеспечивает автоматическое закрытие бизнес‑процессов, которые более не требуют дальнейшего исполнения.

Источник:
- `5.+Модули+и+методы+движка+Бизнес-процессов+в+CRM+(Верхнеуровнево).doc`, «5.1. ОбщийМодуль: лкРегламентныеЗадания»
