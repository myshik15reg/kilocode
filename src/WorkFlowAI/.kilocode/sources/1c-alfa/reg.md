# REG — регламент разработки 1С (firm): операционная выжимка

Это **не** копия первичного документа. Это санитизированная выжимка правил, которые используются в pack как firm‑SoT.

Плейсхолдеры:
- `<TICKET>` — номер заявки/тикета;
- `<USER>` — исполнитель;
- `<DATETIME>` — дата/время;
- `<HOST>` — хост/URL (в pack реальные адреса не фиксируются).

---

<a id="sdlc"></a>
## SDLC: «Заявка → DONE»

<a id="sdlc-task-classification"></a>
### Классификация задач
- **Поддержка**: оценка кодирования < 1 часа.
- **Проектная**: оценка кодирования > 1 часа.

<a id="sdlc-stages"></a>
### Этапы и минимальные результаты (DoD)

Ниже — **минимум артефактов**, который должен быть обеспечен в рамках фирменного процесса.

1) **Заявка**
   - описание требований;
   - при необходимости — виза руководителя заказчика;
   - прикреплённый файл с требованиями;
   - для «поддержки» — предложенное решение в УЗ.

2) **Аналитика** (для проектных задач)
   - согласованные финальные требования;
   - согласованное ТЗ (если требуется);
   - оценка эффекта заказчиком (если требуется);
   - согласованные сценарии тестирования.

3) **Архитектура** (для проектных задач)
   - design review (согласованная концепция);
   - предварительная оценка сроков;
   - задокументированное архитектурное решение (в т.ч. модель данных — при необходимости).

<a id="sdlc-development-gate-changed-objects"></a>
### Гейт разработки: «База изменённых объектов»

**Правило:** все изменения объектов и функционала должны быть описаны разработчиком в «Базе изменённых объектов» заявки.

<a id="sdlc-testing-gate"></a>
### Гейт тестирования: ИТ + бизнес + подтверждение

Этап тестирования включает:
- ИТ‑тестирование;
- бизнес‑тестирование заказчиком/представителем.

**Правило:** после тестирования заказчик **письменно подтверждает** корректную работу функционала или возвращает на доработку.

<a id="sdlc-release-gate-code-review"></a>
### Гейт релиза: Code Review обязателен

**Правило:** перенос в продуктив выполняется только после успешного Code Review.

<a id="traceability"></a>
## Трассируемость изменений (УЗ «База изменённых объектов» + XML)

**Цель:** сделать изменения проверяемыми и релизопригодными.

Правила (firm):
1) **Все изменения** фиксируются в УЗ в таблице «База изменённых объектов».
2) Описание должно однозначно указывать: что изменили и где (объект/модуль/участок кода).
3) Рекомендуется выгружать изменённые элементы в XML и прикреплять к `<TICKET>`.
4) Для незначительных изменений допускается не выгружать XML (описать изменения текстом).

Гейт релиза:
- релиз по заявке отменяется, если база изменённых объектов не соответствует данным в хранилище **или** не пройден Code Review.

---

<a id="storage"></a>
## Хранилище разработчиков (1C Storage)

Ключевые правила (firm):
1) Перед разработкой рекурсивно получить все изменения из хранилища.
2) Захватывать объекты на минимальное время; при возможности захватывать компонент, а не весь объект.
3) Помещать изменения пакетно в рамках одной заявки `<TICKET>`.
4) Перед помещением выполнить «Проверка модулей», без ошибок.

<a id="extensions"></a>
## Расширения (политика и hotfix)

Ограничение области применения:
- новый функционал (включая новые прикладные объекты и изменения/добавление реквизитов и т.п.) реализуется **в расширяемой конфигурации**, а не в расширении.

Hotfix через расширение:
- допустимо использовать расширение **только** с назначением «Исправление» для оперативного исправления;
- после переноса исправления в расширяемую конфигурацию расширение должно быть удалено (или деактивировано, если добавляло данные).

Порядок применения расширений:
- «Исправление» → «Адаптация» → «Дополнение».

Префиксы:
- имена собственных методов/переменных расширяющих модулей — с префиксом расширения;
- все расширения — с префиксом `ал_`.

Формат имени расширения:
- `<TICKET> <USER> <DEADLINE> <SHORT_NAME>`.

<a id="http-swagger"></a>
## HTTP‑сервисы и Swagger (УЗ)

Мини‑процесс (firm):
1) При добавлении нового HTTP‑сервиса — выполнить описание через подсистему «Работа со Swagger» (УЗ).
2) Заполнить данные сервиса в табличной части элемента «Корневой узел URL» (УЗ) (в зависимости от конфигурации).
3) Указать методы и параметры методов.
4) Нажать «Обновить информацию по сервисам».

Безопасность:
- не фиксировать реальные URL/хосты/учётные данные — использовать `<HOST>` и плейсхолдеры.

<a id="integration-overview"></a>
## Интеграции (подтверждённый минимум)

Подтверждённый минимум (firm):
1) Интеграция принята на основе REST API (HTTP‑запросы).
2) Обмен данными — пакетами JSON.
3) Для гарантии доставки и маршрутизации используется RabbitMQ.

Ограничение:
- детальные стандарты (naming, headers, мониторинг и т.п.) — **не фиксируются** здесь до извлечения/санитизации первоисточников.

<a id="coding-standards"></a>
## Стандарты кода и метаданных

<a id="coding-standards-change-comments"></a>
### Комментарии к изменениям в коде

При модификации существующего кода использовать обязательную структуру:

```bsl
// + Альфа-Лизинг. <USER>. <DATETIME>. <TICKET>.
// Описание изменений
// Старый код (если был)
// - Альфа-Лизинг. <USER>. <DATETIME>.
```

<a id="coding-standards-prefixes"></a>
### Префиксы для объектов метаданных

- Новые прикладные объекты: `ал_` + `ИмяОбъекта`.
- Изменение объектов поставщика: новые элементы префиксуются `ал_`.
- Устаревшие объекты метаданных: префикс «Удалить».

<a id="coding-standards-api-doc"></a>
### Документирование программного интерфейса

Процедуры и функции, входящие в программный интерфейс модулей, требуют обязательного комментирования (описание/параметры/возвращаемое/пример).

<a id="access-control"></a>
## Права доступа и роли

Ключевые правила (firm):
1) Роли должны быть **атомарными** (доступ к элементарным функциям), профили пользователей собираются из ролей.
2) Ни одна роль (включая «ПолныеПрава» и «АдминистраторСистемы») не должна давать право на **интерактивное удаление** ссылочных объектов.
3) Устаревшие объекты (с префиксом «Удалить») исключаются из всех ролей, кроме «ПолныеПрава» или «АдминистраторСистемы».
