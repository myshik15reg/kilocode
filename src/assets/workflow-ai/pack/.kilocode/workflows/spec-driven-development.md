# Разработка от спецификации (spec-driven-development)

## Описание
Процесс разработки от спецификации, который выравнивает артефакты Spec Kit (`spec.md`, `plan.md`, `tasks.md`)
с правилами протоколов WorkFlowAI, TDD и 100% покрытием.

## Когда использовать
- Новая фича или значимое изменение, где нужны спецификации и трассируемость.
- Многошаговая работа, где требования должны вести реализацию.

## Входные данные
- Описание фичи (языком бизнеса/ценности).
- Архитектурные ограничения (стек, ограничения, комплаенс).

## Выходные данные
- `spec.md`, `plan.md`, `tasks.md`.
- Обновлённые логи протокола и Memory Bank (если применимо).

## Шаги
1. Принципы / Конституция
   - Если доступен Spec Kit CLI, использовать `/speckit.constitution`.
   - Иначе выровняться по Memory Bank и ограничениям проекта.

2. Спецификация
   - Создать `spec.md`, используя шаблоны Spec Kit или `~/.kilocode/patterns/analysis/requirements-template.md`.
   - Фокус на том, что и зачем делаем; избегать деталей реализации.
   - Приоритизировать пользовательские истории (P1, P2, ...), чтобы у каждой были независимые тесты.
   - Зафиксировать сценарии приёмки (`Given/When/Then`), краевые случаи и критерии успеха.
   - Помечать неясности маркером `[НУЖНО УТОЧНИТЬ: ...]`.

3. Уточнение
   - Закрыть все пункты `[НУЖНО УТОЧНИТЬ]`.
   - Убедиться, что требования тестируемы и измеримы.

4. План
   - Подготовить `plan.md` с техконтекстом, архитектурой и ограничениями.
   - Описать подход к тестированию и безопасности.
   - Если есть constitution, отметить нарушения и обоснование.
   - Добавить матрицу покрытия требований (R# -> задачи).

5. Задачи
   - Сгенерировать `tasks.md` с зависимостями и путями файлов.
   - Формат: `[ID] [P] [Story] Description`.
   - Вставлять тестовые задачи перед задачами реализации.
   - При необходимости группировать задачи по пользовательской истории.
   - Соблюдать 100% покрытие (тесты обязательны).

6. Проверка консистентности
   - Использовать `/speckit.analyze` (если доступно) или провести ручной review.
   - Устранить расхождения между spec/plan/tasks до начала реализации.

7. Реализация
   - Следовать TDD (Red-Green-Refactor).
   - Обновлять чекбоксы `tasks.md` по мере выполнения задач.
   - Запускать тесты, линт и проверки покрытия.

8. Завершение
   - Обновить лог выполнения протокола (`execution.md`).
   - Обновить Memory Bank, если изменились архитектура, продукт или техстек.

## Примечания
- Для любой работы веди протокол в `.protocols/`.
- Если используешь Spec Kit CLI, спеки обычно живут в `specs/NNN-feature-name/`.
- Для `brownfield`-дельт предпочитай процесс изменений OpenSpec.

## Чеклист
- [ ] `spec.md` заполнен и уточнён
- [ ] `plan.md` заполнен и одобрен
- [ ] `tasks.md` содержит тесты и зависимости
- [ ] есть матрица покрытия требований
- [ ] тесты проходят, покрытие = 100%
- [ ] протокол и Memory Bank обновлены
